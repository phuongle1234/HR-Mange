# Conventions

Draft database specification. No Prisma schema or migration is created in this phase.

## Purpose
Define naming, typing, and structural conventions so every entity spec and future Prisma schema stays consistent.

## Naming
- Table names: `snake_case`, plural (`users`, `employees`, `audit_logs`).
- Prisma model names: `PascalCase`, singular (`User`, `Employee`, `AuditLog`), mapped to the table name with `@@map`.
- Column names: `camelCase` in the Prisma schema/TypeScript, mapped to `snake_case` in PostgreSQL with `@map` (e.g. `employeeCode` maps to `employee_code`).
- Foreign key columns: `<referencedEntity>Id` (e.g. `departmentId`, `performedByUserId`).
- Enum types: `PascalCase` type name, `UPPER_SNAKE_CASE` values (e.g. `EmployeeStatus.ON_LEAVE`).

## Primary Keys
- Every table has a single-column primary key `id`.
- Type: `uuid`, generated by the database (extension/strategy pending implementation).
- Auto-increment integer IDs are not used, to avoid leaking record counts and to simplify future multi-environment data handling.
- Exception: `organizations.id` is `Int @default(autoincrement())` — a deliberate, recorded deviation. See `docs/04-database/entities/organization.md` ("Deviation from DB-CONVENTIONS") for why, and how the rest of the system (`BaseService`'s audit `entityId`) accounts for a non-UUID key.

## Timestamps
- Every table has `createdAt` and `updatedAt`, type `timestamptz`, stored in UTC.
- `createdAt` defaults to `now()` and is immutable after insert.
- `updatedAt` is maintained by Prisma's `@updatedAt` on write; application code must not set it manually.

## Soft Delete (Candidate, Pending Approval)
- If an entity adopts soft delete, it gets a nullable `deletedAt timestamptz` column.
- A non-null `deletedAt` means the row is excluded from normal reads; repositories must filter it explicitly rather than relying on the ORM to hide it implicitly.
- Which entities, if any, use soft delete is not decided — see the delete-strategy ambiguity in `DB-EMPLOYEE` and `BUSINESS-EMPLOYEE`.

## Nullability & Defaults
- A column is nullable only when the field is explicitly optional in the matching business/API spec.
- Default values are only added when a spec states the default explicitly; no implicit defaults are invented at the database layer.

## Auditability
- Tables whose rows are created/modified by a user (`Employee`) carry `createdByUserId` / `updatedByUserId` nullable foreign keys to `User`, for traceability independent of `AuditLog`.

## Pending Decisions
- UUID generation extension/strategy.
- Case sensitivity for unique string columns (`email`, `employeeCode`).
- Which entities use soft delete vs hard delete.
